# OpenCR 카메라 제어 진행 기록

작성일: 2026-10-02 (한국 시간)

이 문서는 이전 진행 메모, 이번 대화, 로컬 소스와 실제 장비 조회 결과를 바탕으로 정리했다. 터미널 원문이 남아 있는 결과는 그대로 인용하고, 사용자가 관찰한 결과와 미확인 사항은 따로 표시했다. 모든 시험의 전체 출력이 보관된 것은 아니다.

## 1. 목표와 과제 범위

목표는 인지 프로그램이 보내는 목표 오차를 받아 카메라를 회전시키는 제어 시스템이다.

```text
카메라 → 인지 → /target → 제어 프로그램 → OpenCR → Dynamixel
PC → SSH → Raspberry Pi → USB Serial → OpenCR → 두 축 카메라
```

기존 계획은 수평 1축 객체 추적이다. 이번 작업에서는 실제 장비에 좌우·상하 두 축이 있어, 두 모터 확인과 기본 위치 명령·홈 복귀·자세 유지 기능까지 만들었다.

함께 읽은 `과제2_turtlesim_ROS2패키지.md`는 별도 ROS 2 과제다. C++ 기초, rclpy/rclcpp, Service/Action, 인터페이스, QoS, launch, 시각화·rosbag·pytest를 요구한다. 문서에는 5~9번이 선택 과제로 표시되어 있다. 이번 세션에서 turtlesim 패키지를 구현하거나 실행한 것은 아니다.

## 3. 장비 확인 결과

| 항목 | 좌우 축 | 상하 축 |
|---|---|---|
| 사용자 지정 축 | X / pan / 팬 | Y / tilt / 틸트 |
| 모터 ID | **11** | **12** |
| 모델 | XM430-W350 | XM430-W350 |
| 모델 번호 | 1020 | 1020 |
| 모터 펌웨어 버전 | 50 | 50 |
| 통신 | Protocol 2.0 / 1 Mbps | Protocol 2.0 / 1 Mbps |
| 조회된 전압 | 12.0 V | 12.0 V |
| 저장한 홈 엔코더 | **4067틱** | **2116틱** |
| Homing Offset | 0 | 0 |
| 양수 방향 | 사용자 관찰: 왼쪽 | 위/아래 중 어느 방향인지 아직 기록 없음 |

`OpenCR_Virtual_ComPort_in_FS_Mode`라는 USB 이름은 보드 정보이며 모터 모델이 아니다. 모델과 ID는 OpenCR의 Dynamixel 버스를 통해 직접 조회했다.

### ID 확인 방법

1. 포트를 다른 프로그램이 사용하는지 확인한다.
2. 읽기 전용 진단 펌웨어를 OpenCR에 업로드한다.
3. 시리얼로 `scan`을 보내 OpenCR에서 PING과 READ를 수행한다.

```bash
ls -l /dev/ttyACM*
fuser /dev/ttyACM0
```

핵심 조회 코드:

```cpp
dxl.setPortProtocolVersion(2.0);
dxl.begin(1000000);
for (uint8_t id = 11; id <= 12; ++id) {
  if (dxl.ping(id)) {
    Serial.println(dxl.getModelNumber(id));
  }
}
```

최초 진단 프로그램은 첫 모터를 찾으면 종료했으므로 ID11만 출력했다. 사용자가 두 모터가 연결되어 있다고 알려준 후, ID11과 ID12 모두 조회하도록 별도 진단 스케치를 만들었다.

실제 출력:

```text
FOUND id=11 baud=1000000 protocol=2 model=1020
FOUND id=12 baud=1000000 protocol=2 model=1020
SCAN_DONE: both IDs checked; settings unchanged.
```

진단 스케치는 모터 설정 변경·구동 명령을 보내지 않는다. 다만 펌웨어 업로드는 보드를 재시작하며, 보드가 모터 버스 전원을 켤 수 있다. 진단 프로그램 자체가 기존 모터 토크나 목표값을 반드시 초기화하는 것은 아니다.

## 4. 작업 순서와 실제 시험

### 4.1 기존 위치 P 제어 코드 확인

처음 열린 `opencr_position_p.ino`는 XM430-W210 / ID1 설정이었다. W350 / ID12 백업도 있었다. 실제 모터 확인 후 좌우 시험을 위해 W350 / ID11로 변경했고, 이후 상하 시험을 위해 ID12로 변경했다.

기존 제어 방식:

```text
시작 위치를 0도로 저장
→ 2초 후 목표 각도 적용
→ OpenCR에서 위치 오차 × Kp 계산
→ Goal Velocity 명령
→ 엔코더 피드백
```

기존 명령:

```text
s <Kp> <최대속도_deg_s|max> <상대각도_deg>
k 0.3
v 5
a 10
x
```

속도 모드에서 OpenCR의 외부 P 제어를 사용하며, 모터 내부 위치 PID를 사용하는 방식은 아니다.

### 4.2 좌우 축 시험

시험 안내 명령:

```text
s 0.3 5 10
```

사용자가 실제로 좌측 회전을 확인했다. 따라서 ID11은 양수 목표에서 왼쪽으로 회전한다.

45°·90° 시험과 `s 4.5 20 90` 사용법을 안내했으나, 그 모든 명령의 실제 실행·도착 결과가 확인된 것은 아니다.

중요한 기준: 기존 `s` 명령은 매번 시작 위치를 새 0도로 잡는다. 이전에 이동한 위치에서 또 90°를 입력하면 이전 기준의 90°로 돌아가는 것이 아니라 현재 위치에서 추가 이동한다.

### 4.3 상하 축 준비

ID12 / W350로 수정·빌드·업로드했다. 구동 전 설정 확인 결과:

```text
P SET Kp=0.3000, Ki=0.0000, Kd=0.0000, speed_limit_deg_s=3.000, angle_deg=5.000
```

시험 명령으로 `s 0.3 3 5`를 안내했다. 상하 양수 방향과 실제 도착 결과에 대한 사용자 확인은 기록에 없다.

### 4.4 원위치 저장

사용자가 정상 자세를 정하고 복귀 순서를 **상하 먼저, 좌우 다음**으로 지정했다. 모터 정지·자세 유지·시리얼 모니터 종료를 확인한 뒤 엔코더를 읽었다.

실제 조회:

```text
ID11: home_position_ticks=4067, velocity_raw=0, homing_offset=0
ID12: home_position_ticks=2116, velocity_raw=0, homing_offset=0
```

원위치는 카메라 제어 스케치의 상수로 저장했다. 홈을 EEPROM에 저장한 것은 아니다. EEPROM에는 이후 추가한 자동 복귀 설정만 저장한다.

좌우 홈이 4096틱 경계 근처이므로, 경계를 넘을 때 긴 방향으로 회전하지 않도록 가까운 홈 분기를 계산한다. 누적 위치와 자세 유지에는 Extended Position 모드를 사용한다.

### 4.5 초기 자동 홈 복귀 구현

초기 `opencr_camera_home.ino`는 보드 시작 시 자동으로 12번 → 11번 복귀했다. 목표 도착 후 토크를 유지하고, `x`도 토크 해제 대신 현재 위치 유지로 바꾸었다.

당시 실제 출력:

```text
HOMING ID 12 target=2116
HOME reached ID 12
HOMING ID 11 target=4067
HOME reached ID 11
HOME_DONE: tilt then pan; torque remains ON.
ID 12 position=2115
ID 11 position=4067
```

이 확인은 이미 홈 근처에서 수행한 시험이다. 크게 처진 카메라를 들어 올리는 시험까지 성공했다는 의미는 아니다.

### 4.6 카메라 처짐과 재연결 확인

사용자는 전원을 끄면 카메라가 무게 때문에 아래로 내려간다고 설명했다. 토크가 켜진 상태에서 손으로 억지로 축을 돌리지 않도록 안내했다.

재연결 후 홈 펌웨어에서 두 축 위치가 0으로 출력되고 다음 오류가 나왔다.

```text
FAULT: communication or hardware error
```

읽기 전용 진단 펌웨어로 다시 확인한 결과:

```text
ID11: position=3981, torque_enable=0, hardware_error=0, voltage=12.0V
ID12: position=726, torque_enable=0, hardware_error=0, voltage=12.0V
```

이 시점에는 두 모터의 통신과 하드웨어 오류가 정상으로 확인되었다. 이전 통신 FAULT의 정확한 발생 원인은 확정하지 못했다. 두 축의 0 출력 역시 정상 홈 도착으로 취급하지 않았다.

상하 홈과 차이는 `2116 - 726 = 1390틱`, 약 122.2°였다. 이는 당시 90° 복귀 제한을 넘었다. 다만 이것이 앞선 `communication or hardware error`의 원인이라고 확정한 것은 아니다.

사용자가 자세를 잡을 때 아래로 당기는 느낌을 말했으나, 이후 **연결선이 당기고 있었음**을 확인했다. 모터 자체 이상으로 판정하지 않았다.

### 4.7 명령 형식과 자세 유지 변경

사용자는 `s Kp 속도 각도` 시험 방식 대신 목적에 맞는 카메라 명령을 원했다.

기존 P 시험 코드는 목표에 도착해서 종료되는 것이 아니라 실행 시간 제한에 도달하면 정지·토크 OFF한다. 기본 최소 실행 시간은 60초이며, 입력 속도와 각도에 따라 더 길어질 수 있다. 프로그램 자체가 종료되는 것은 아니다. 토크 OFF 후에는 카메라가 무게로 처질 수 있다.

새 코드는 모터 내부 위치 제어를 사용한다. 이동이 끝나면 자세를 계속 유지하며, 게인을 매 명령에 입력하지 않는다. 이는 기존 외부 P 제어 실험과 제어 방식이 다르다.

현재 명령:

| 명령 | 의미 |
|---|---|
| `pan 30` | 좌우 홈 기준 +30°로 이동 |
| `tilt -10` | 상하 홈 기준 -10°로 이동 |
| `speed 5` | 이후 이동 속도 설정 |
| `h` | 상하 홈 복귀 완료 후 좌우 홈 복귀 |
| `x` | 현재 위치에서 정지·유지; 줄바꿈을 기다리지 않음 |
| `off` | 두 모터 토크 해제; 카메라 지지 필요 |
| `p` | 상태·위치·토크·하드웨어 오류 출력 |
| `auto on` | 보드 시작 시 홈 복귀 설정을 EEPROM에 저장 |
| `auto off` | 보드 시작 시 명령 대기 설정을 EEPROM에 저장 |

기본값은 자동 복귀 OFF, 속도 5°/초이다. 이동 중 다른 이동 명령은 BUSY로 거부하며, `x`로 정지한 뒤 변경한다. Backspace 처리도 추가했다.

### 4.8 최신 사용자 시험

사용자가 `pan 30`을 입력했고, 다음 완료 메시지가 떴다고 확인했다.

```text
REACHED pan
DONE: holding position; no automatic torque off.
```

좌우 +30° 이동과 완료 상태 전환은 확인됐다. 시간 제한 없이 장시간 자세 유지하는 시험은 아직 별도로 기록하지 않았다.

이후 `h` 복귀 시험을 안내했지만 실제 완료 여부에 대한 답변은 아직 없다.

## 5. 오류와 해결 기록

| 증상 | 확인 내용 / 원인 | 조치 / 결과 |
|---|---|---|
| 문서 경로가 없음 | `/home/haeminkim/...`는 현재 `/home/pa06` 환경에 없음 | 사용자가 문서를 sketches에 옮긴 후 읽음 |
| 포트 사용 중 | `miniterm` 프로세스가 `/dev/ttyACM0` 사용 | Ctrl+]로 종료 확인 후 업로드·조회 |
| 최초 검색에 ID11만 보임 | 원본 진단은 첫 모터 발견 시 종료 | 두 ID를 각각 조회해 ID12도 확인 |
| `FAULT: RESET required` | 초기 오류 원인이 시작 때만 출력되어 파악 어려움 | 오류 이유를 저장하고 명령 응답에도 출력하도록 수정 |
| `Reason: requires XM430-W350` | 수정 과정에서 안내 문구만 W350로 바뀌고 비교 상수 `XM430_W210`이 남음 | `XM430_W350`으로 수정, 재빌드·업로드, 설정 응답 정상 확인 |
| miniterm `Exception in thread rx` | `SerialException: device reports readiness to read but returned no data (device disconnected or multiple access on port?)` | RESET 시 USB 재연결 가능성을 확인하고 모니터 재실행 안내. 정확한 단절 원인은 확정하지 않음 |
| 입력 글자가 안 보임 | miniterm 기본 로컬 에코 OFF 가능성 | `-e` 옵션 또는 Ctrl+T 후 E로 입력 표시 |
| `Invalid setting...` | 잘못된 형식, 쉼표, 입력 잔여 문자, Backspace 문자 등이 가능한 원인 | 공백 구분·새 줄 재입력 안내. 사용자가 `P SET Kp=0.3000` 정상 응답 확인. 모든 발생 건의 원문 입력은 없어 각각의 원인을 확정하지 못함 |
| 실행 중 설정 변경 불가 | 기존 코드가 실행 중 설정 변경을 차단 | `x` 정지 후 변경 |
| 시험 종료 후 카메라 처짐 | 기존 P 코드가 실행 시간 종료 시 토크 OFF | 새 카메라 코드에서 완료·정지 후 위치 유지 |
| 재연결 후 통신/하드웨어 FAULT | 재진단에서는 전압·하드웨어 오류 정상 | 원인은 미확정; 임의로 모터 고장이라고 결론 내리지 않음 |
| 크게 처진 위치에서 홈 제한 초과 | 상하 홈까지 약 122.2°, 기존 제한 90° | 최신 코드에서 상하 범위 ±135°, 좌우 ±90°로 분리 |
| 아래로 억지로 당기는 느낌 | 사용자 확인: 케이블 당김 | 케이블 여유와 경로 확보 필요 |
| `speed 50` 거부 | 최신 코드 상한 30°/초 | 원인 설명만 완료. 50°/초 수정·업로드는 아직 하지 않음 |

일부 업로드 직후 조회에서 첫 줄만 `Invalid setting` 또는 도움말이 출력되고 다음 정상 명령은 처리됐다. 부팅/업로더 이후 입력 잔여 문자가 의심되지만 원인을 확정하지 않았다.

현재 제약 사항:

- pan은 홈 기준 ±90°, tilt는 ±135°이다. 기구의 실측 안전 범위가 아니라 소프트웨어상의 시험 범위다.
- speed는 1.374~30°/초이다. 모터의 속도 단위에 맞춰 내림 처리하며, 모터 측 Velocity Limit도 확인한다.
- 통신 감시에는 Bus Watchdog을 사용한다. 통신이 정상이면 도착 후에도 위치 유지가 계속된다.
- 동작 시간 초과나 통신·하드웨어 이상은 FAULT로 처리하여 정지한다. 위치 유지가 불가능하면 토크 OFF를 요청하므로, 자세 유지를 항상 보장하는 것은 아니다.
- 자동 복귀 설정은 EEPROM에 저장한다. 실제 장비에서 `auto on`을 설정하고 전원을 다시 켜서 검증한 기록은 아직 없다.
- 자동 복귀는 OpenCR 프로그램 시작 시 수행한다. USB로 보드가 계속 동작하는 상태에서 모터 전원만 껐다 켜는 것은 프로그램 재시작과 다를 수 있다.
- 단일 회전 기준의 홈 위치만으로는 케이블이 감긴 상태를 판별할 수 없다. 손으로 여러 바퀴 돌리는 용도는 지원하지 않는다.

## 9. 다음에 할 일

### 하드웨어와 기본 동작

1. 케이블 여유, 위·아래 방향의 간섭, 카메라 고정 상태를 확인한다.
2. `p`로 현재 위치·토크·오류를 확인한다.
3. `h`로 상하 한 번, 좌우 한 번의 복귀 순서와 실제 홈 자세를 확인한다.
4. `tilt`에 작은 양수·음수 각도를 입력하여 위·아래 방향을 기록한다.
5. 카메라를 지지한 상태에서 `off`, 작은 자세 변경, `h`를 통한 복귀를 시험한다.
6. 실제로 카메라가 크게 처진 상태에서 복귀할 수 있는지 확인한다.
7. 장시간 자세 유지 여부를 확인한다.
8. 완전한 복귀를 확인한 뒤, 필요하면 `auto on`을 저장하고 보드 시작 시험을 한다.
9. 50°/초 지원이 필요하면 속도 상한을 변경하여 다시 빌드·업로드하고, 먼저 부하가 작은 축에서 검증한다.

### ROS 2 제어 계획 (아직 미구현)

이전 진행 메모에 있는 계획:

- Raspberry Pi의 ROS 2 설치 상태 확인.
- `/target`을 `geometry_msgs/msg/PointStamped`로 수신.
- `point.x`는 수평 정규화 오차이며, `point.z=0`은 목표 없음을 의미.
- 정상 입력이 끊기면 기본 0.5초 후 정지.
- 모터 없이 모의 입력으로 양수·음수 방향, 목표 소실, 시간 초과 시험.
- `command = clamp(direction × Kp × ex, -speed_limit, +speed_limit)` 방식의 외부 제어.
- IDLE / TRACKING / LOST 상태, 데드밴드, 각도 제한, CSV 기록.
- 통신 단절 시 정지와 모터 부하를 포함한 최종 실제 장비 시험.

현재 카메라 위치 명령을 이 추적 제어에 어떻게 연결할지는 다음 설계 과제다. 내부 위치 제어 버전을 그대로 외부 P 제어 과제의 수행 실적으로 취급하지 않는다.
